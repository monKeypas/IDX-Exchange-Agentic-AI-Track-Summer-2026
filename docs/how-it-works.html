How It Works

What the project actually is, in plain language — then the words to say during the demo, and answers to the questions you're most likely to get.

Start here

What you built, in one paragraph

It's a real-estate assistant you talk to over WhatsApp. You text it in ordinary English — "find me 3-bedroom homes in Pasadena under $1.2 million" — and it works out what you're asking, looks up real listings in a database, and texts back an answer. It handles eight different kinds of question, remembers the conversation so you can refine your search one message at a time, and can write an email for you. It will never send that email until you personally say the word.

If you can say that paragraph and then explain the six ideas below, you can carry the whole presentation. Everything else is detail.

The six ideas

What's actually going on

Idea 1 — Skills

Six specialists, each with one job

Rather than one big program that does everything, the project is split into six skills. One searches listings. One does market statistics. One finds similar homes. One does meaning-based search. One answers definition questions. One writes emails.

A skill is just a folder containing some code and a description file (SKILL.md) that explains what it does and how to run it.

Analogy: a firm where each person handles one type of request. Nobody does everything; everyone is good at their one thing.

Idea 2 — The orchestrator

Something has to decide who answers

When a message arrives, a function called classifyIntent reads it and decides which specialist should handle it. It looks for signals: words like "find" or "3 bedroom" mean a property search; words like "market" or "prices rising" mean statistics; "what does X mean" means a definition question.

If a message asks two things at once — "find me homes AND tell me if prices are rising" — it sends the message to two specialists at the same time and combines their answers into one reply.

Analogy: the receptionist who reads your request and routes you to the right desk — and occasionally to two desks at once.

Idea 3 — Two databases

What's for sale vs. what actually sold

rets_property holds homes currently for sale. california_sold holds homes that have already sold.

You need both because they answer different questions. "Show me 3-bedroom condos" is about what's available now. "Are prices rising?" or "is this listing overpriced?" can only be answered from what things actually sold for.

The irritating part — and a good thing to mention — is that the two tables name the same things differently. City is L_City in one and just City in the other. Bedrooms are L_Keyword2 in one and BedroomsTotal in the other. That mismatch caused real bugs.

Idea 4 — Embeddings

Turning meaning into numbers

A normal database search matches words. Ask for "cozy cottage" and a listing described as "charming bungalow" won't come back — no words in common — even though it's exactly what you meant.

An embedding fixes that. A model reads a piece of text and turns it into a list of 384 numbers, arranged so that text with similar meaning ends up with similar numbers. Compare two of these lists mathematically (that's cosine similarity) and you get a score for how alike they mean.

The project does this to L_Remarks — the agent's written description of each home. So "charming craftsman with mountain views" finds listings that read like that, even with no matching words.

Analogy: giving every listing a location on a giant map of meaning, then asking "what's nearest to this spot?"

Idea 5 — RAG

Look it up before answering

Language models will confidently invent answers. RAG — retrieval-augmented generation — stops that by making the model read the source first.

Your reference documents get chopped into ~900-character chunks and embedded (same trick as above). When someone asks "what does DOM mean?", the system finds the 4 chunks closest in meaning to the question, hands them to the model, and says: answer using only this.

That's why the reply lists its sources — and why it can say it doesn't know instead of making something up.

Idea 6 — The approval gate

The part that deliberately doesn't work automatically

The assistant can write an email. It cannot send one on its own, ever. Drafting and sending are two separate steps with a human in the middle.

When you ask for an email, it writes one, saves it with an ID, and marks it pending approval. Nothing leaves. Only when a person replies "approve" does a second, separate piece of code send it — and that code refuses to run unless approval was explicit.

This is the single most important thing in the project. An assistant that can email people on your behalf without asking is genuinely dangerous, and the whole design treats that as non-negotiable.

The story

Why it was built in that order

If someone asks how the project developed, this is the arc — each week solving a problem the previous week created.

Weeks 1–2 — Work out the shape of the system, then teach it to read English: turn "3-bedroom condo in Irvine under $1.5M" into structured filters a database can use.

Week 3 — Connect those filters to the real database and get actual listings back.

Week 4 — People don't ask one perfect question; they refine. So add memory, letting each message build on the last instead of starting over.

Week 5 — Searching isn't enough. "Should I buy now?" needs the sold-history table: medians, days on market, trends, inventory.

Week 6 — Some searches can't be expressed as filters at all. Embeddings handle description rather than specification.

Week 7 — Combine both: recommend similar homes using structured similarity and meaning similarity, then sanity-check the price against real comparable sales.

Week 8 — Users ask questions that aren't searches at all ("what's escrow?"). RAG answers from documents rather than the database.

Weeks 9–10 — Six separate tools is not a product. The orchestrator makes them one assistant behind a single WhatsApp number.

Week 11 — Give it the ability to email, and immediately constrain it: draft, human approval, then send.

The mechanics

Under the hood

This section goes a level deeper on the pieces people ask about most. You don't need all of it to present — but knowing two or three of these properly is what separates "I can describe my project" from "I understand my project".

1. How classifyIntent actually decides

It's pattern matching, not AI. Six regular expressions each look for the vocabulary of one kind of request:

SEARCH → find, show, homes, beds, bedrooms, condo, pool, under $ … MARKET → market, median, trend, days on market, good time to buy … RECOMMEND → similar, recommend, homes like, i like … KNOWLEDGE → what does, what is, define, meaning of, escrow, cap rate … EMAIL → email, draft, compose, write me an email … APPROVE → approve, send it, confirm, ship it …

Each pattern is wrapped in \b — a word boundary, meaning "this must be a whole word". That's what stops "bedroom" from matching inside "bedrooms" — and it's exactly the bug that broke multi-turn refinement until the patterns were changed to bedrooms?, where the ? makes the final "s" optional.

The order the checks run in is the real logic, and every line of it is deliberate:

  1. Approval first. "Send it" must never be read as a request to write an email. Approval acts on a draft that already exists, so it's checked before anything can create one.
  2. Search + market together → mixed. If a message trips both patterns, it isn't one or the other — it's both, and both agents run.
  3. A question that asks what a term means is pulled away from market stats. "DOM" stands for days on market, so it sits in the market vocabulary — which means "What does DOM mean?" trips the market pattern even though it's really a dictionary question. A guard catches that: if the sentence opens with "what does / what is / what are", treat it as a definition and ignore the market match, sending it to RAG instead.

    The guard needs a second half, though, because plenty of real market questions also open that way — "What is the median price in Irvine?" is asking for a number, not a definition. So it only counts as definitional if the sentence contains no measurement words (average, median, price per, inventory, trend). Term question → RAG; number question → market stats.
  4. Structured search beats descriptive search. If real filters are present, use the database properly. Semantic search is the fallback for language that has no filters in it.
  5. Anything left that's three or more words becomes semantic search — unless it's a greeting, which is filtered out separately so "hey thanks" doesn't get treated as a property description.

Every one of those routes is locked down by a unit test, so changing a keyword can't silently re-route existing queries without a test failing.

2. How English becomes a database query

parsePropertyQuery runs one regex per field and assembles a filter object. Money is the fiddliest part, because people write budgets a dozen ways:

$900,000maxPrice 900,000commas stripped before parsing

City extraction is the one piece of genuine cleverness. It looks for "in <something>" but has to know where the city name stops — in "homes in Pasadena and tell me whether prices are rising", the city is Pasadena, not "Pasadena and tell me whether". So the pattern stops at a list of following words like under, with, and, tell, between, built. There's also a small blocklist rejecting non-cities like "bay area" and "any city", and the result gets title-cased, so "san jose" becomes "San Jose".

3. How the database is asked, without letting users hijack it

SQL is the language for asking a database questions. A simple one looks like this:

SELECT * FROM rets_property WHERE L_City = 'Irvine'

"Give me every row from the listings table where the city is Irvine." Your filters have to be turned into a sentence like that. The obvious way to do it is to glue the user's words straight into the text — and that is exactly the dangerous way.

Why gluing is dangerous. Suppose you build the sentence by pasting whatever the user typed where the city goes. Normally that's fine. But someone types this as their city:

Irvine'; DROP TABLE rets_property; --

Glue that in and the database receives:

SELECT * FROM rets_property WHERE L_City = 'Irvine'; DROP TABLE rets_property; --'

You meant to ask one question. What arrived was a question and a command to delete the table. The database can't tell the difference, because by the time it sees the sentence, the user's text has become part of the instructions. That attack is called SQL injection, and it's one of the oldest ways to destroy or steal from a database.

The fix: leave blanks. Instead of gluing values in, you write the sentence with ? where each value belongs, and hand the values over separately:

the sentence: SELECT * FROM rets_property WHERE L_City = ? the values: ["Irvine"]

The database reads the sentence first and works out its shape — this is a lookup, filtered by city — and only then fills the blank. Whatever is in that blank is treated as a plain piece of text. If someone submits the malicious city above, the database dutifully searches for a city literally named Irvine'; DROP TABLE…, finds nothing, and returns zero rows. It is never read as a command.

Analogy: a fill-in-the-blank form versus a blank sheet of paper. If you hand someone a contract with blanks, they can only fill the blanks. If you let them write the whole contract, they can add any clause they like.

How the code builds both halves at once. It walks your filters one at a time. Each filter that has a value adds a blank to the sentence and adds its value to the list — always in the same order, so blank #1 matches value #1:

// starting point sentence = "SELECT ... WHERE L_Status = 'Active'" values = [] // city is set → add a blank, add the value sentence += " AND L_City = ?" values.push("Pasadena") // max price is set → add another sentence += " AND L_SystemPrice <= ?" values.push(1200000) // bedrooms is set → and another sentence += " AND L_Keyword2 >= ?" values.push(3)

Filters you didn't mention are skipped entirely, so the sentence only ever contains conditions that matter. What finally goes to the database is:

SELECT ... WHERE L_Status = 'Active' AND L_City = ? AND L_SystemPrice <= ? AND L_Keyword2 >= ? ["Pasadena", 1200000, 3]

This is what "no string concatenation of user input" means, and it's why SQL injection isn't possible here — not because anything is being filtered or cleaned, but because user text never gets to be part of the instructions in the first place.

3b. Why asking for a pool is more awkward than it should be

You'd expect a "has a pool" column to hold true or false. It doesn't — it holds text, and the text isn't consistent. Across the data, the same "yes" shows up as 'True', as '1', and as 'Yes'.

So a check for one spelling quietly misses most of the matching homes — and it doesn't look like a bug, it looks like there just aren't many houses with pools. Every amenity check therefore asks for all three:

AND (PoolPrivateYN = 'True' OR PoolPrivateYN = '1' OR PoolPrivateYN = 'Yes')

The same applies to views, garages, fireplaces, and spas. It's a small thing, but it's a good example of real-world data being messier than the schema suggests — and a genuinely useful thing to mention if you're asked what surprised you.

4. How the conversation remembers

Each user gets a session keyed to their WhatsApp ID, holding the filters gathered so far. Every new message is parsed on its own, then merged onto what's stored — and the merge rule is deliberately simple: anything the new message didn't mention is left alone.

So after "homes in Pasadena", the session holds a city. "Under $1.2M" parses to a price and nothing else, so the city survives. "Only 3 bedrooms" adds bedrooms, and both earlier values survive.

There's also a readiness check before searching. It won't run a query until it has a location, a price bound, and at least one preference — and if something's missing it asks for exactly that one thing rather than dumping thousands of listings or a generic "tell me more".

5. What a transformer is

A transformer is a type of neural network, invented in 2017, that essentially every modern language model is built on — ChatGPT, Claude, and the small model used here are all transformers of different sizes.

Its defining trick is called attention. When the model processes a word, it looks at all the other words in the passage and decides which ones matter for understanding this one. That's what makes it good at language, because words don't mean anything on their own:

"river bank" → attention notices "river" → a bank of earth "savings bank" → attention notices "savings" → a financial institution

Same word, two completely different meanings, and the model produces a different set of numbers for each because it read the surrounding context. An older technique that assigned one fixed vector per word could never do that.

The model repeats this in layers — each layer takes the previous layer's output and refines it, so understanding builds up gradually. The name all-MiniLM-L6-v2 tells you the size: L6 means six layers. That's small — larger models have dozens — and small is exactly why it runs on a laptop in a fraction of a second instead of needing a server with a GPU.

5b. From a listing to 384 numbers

Yes — every token gets its own 384-number vector. That's the part your question was getting at, so here it is concretely.

The listing is first flattened into a paragraph: type, city, beds, baths, square footage, year, price, then the agent's written remarks. That paragraph is split into tokens — roughly word-pieces, so "craftsman" might be one token while an unusual word gets split into two or three.

Each token goes through the six layers and comes out as 384 numbers. So a listing of, say, 150 tokens produces a grid of 150 rows × 384 columns. Crucially, thanks to attention, each of those rows already carries information about the whole passage, not just its own word.

But you need one vector for the listing, not 150. That's what mean pooling does.

5c. How the averaging actually works

It averages column by column. The first number of the result is the average of every token's first number; the second is the average of every token's second number; and so on across all 384.

Here's the real operation on a toy version — 4 tokens, and 4 numbers each instead of 384:

1 2 3 4 charming 0.8 0.1 -0.3 0.5 craftsman 0.6 0.4 -0.1 0.2 with 0.0 0.1 0.2 0.0 views 0.2 0.9 0.4 -0.1 ──────────────────────────── average 0.4 0.375 0.05 0.15 ← the passage vector

Column 1: (0.8 + 0.6 + 0.0 + 0.2) ÷ 4 = 0.4. Column 2: (0.1 + 0.4 + 0.1 + 0.9) ÷ 4 = 0.375. And so on. Four rows go in, one row comes out — same width, no longer per-token.

The real thing is identical, just wider: 150 rows of 384 numbers averaged down to a single row of 384. Padding tokens (filler added to make batches the same length) are left out of the average so they don't drag it toward nothing.

Why averaging isn't as crude as it sounds: because of attention, every token's vector has already absorbed context from the rest of the passage. You're not averaging 150 isolated word meanings — you're averaging 150 context-aware summaries, each of which already knows roughly what the passage is about.

5d. Then it's scaled to length 1

The last step divides every number by the vector's length, so the result always has a length of exactly 1. Continuing the same example:

average 0.4 0.375 0.05 0.15 length = √(0.4² + 0.375² + 0.05² + 0.15²) = 0.5706 normalized 0.701 0.657 0.088 0.263 ← length is now exactly 1

Every number shrank, but their proportions to one another didn't change at all — the vector still points in precisely the same direction, it's just a standard length now.

That matters because a 400-word listing description and a 40-word one would otherwise produce vectors of very different magnitudes, and the long one would dominate comparisons purely for being long. After normalizing, only direction — meaning — is left to compare.

These 384 numbers are the listing's position on a map of meaning. They're computed once and cached to disk, which is why search is instant at demo time: the expensive work already happened during embed:build.

6. What cosine similarity actually computes

Given two vectors, it measures the angle between them — not the distance:

similarity(a, b) = (a · b) / (‖a‖ × ‖b‖) where a · b = a₁b₁ + a₂b₂ + … + a₃₈₄b₃₈₄ (the dot product) ‖a‖ = √(a₁² + a₂² + … + a₃₈₄²) (the vector's length)

The result runs from 1 (pointing the same way — nearly identical meaning) through 0 (unrelated) to −1 (opposite). Dividing by both lengths is what cancels out magnitude, so only direction counts.

Angle is the right measure because a long, flowery description and a short blunt one can mean the same thing — they'd point the same way but have very different magnitudes. Straight-line distance would call them different; cosine correctly calls them similar.

Because the vectors were already normalized to length 1, both denominators are 1, so this reduces to just the dot product. Searching compares the query against every cached listing one by one, sorts by score, and keeps the top 5 — a brute-force scan, which is perfectly fast at this dataset's size.

7. How recommendations combine both approaches

First it works out which home you meant — by matching an address if you gave one, otherwise by semantic search on your description. Then it scores every other listing out of 100:

So roughly 60 points of hard facts and 40 points of meaning. Top 5 by total score, then each is price-checked against homes that actually sold in that city within ±20% of its square footage over the last 6 months — turning "similar" into "similar, and fairly priced".

8. What RAG is actually searching

"Reference documents" sounds vague, so here is exactly what they are. Five Markdown files you wrote, sitting in skills/rag/knowledge/, totalling about 15,000 characters:

FileContainsAnswers questions like
real-estate-glossary.mdPlain-language definitions: DOM, escrow, comps, cap rate, list-to-close"What does DOM mean?"
mls-field-definitions.mdEvery column in both tables and what it holds"What columns are in california_sold?"
ca-real-estate-law.mdCalifornia disclosures — TDS, natural hazard, seismic, lead paint, Megan's Law"What is a natural hazard disclosure?"
market-reports.mdHow to read the Week 5 metrics"What does list-to-close tell me?"
idx-internal.mdHow this product itself works — skills, tables, routing"Which skill handles recommendations?"

What a chunk is. Those five files get sliced into 21 chunks in total — pieces of about 900 characters each. Roughly a healthy paragraph. Here's a real one, the whole DOM entry from your glossary:

## DOM (Days on Market) DOM means Days on Market: how many days a listing was (or has been) publicly on the market. In `california_sold` the column is DaysOnMarket (time until the sale went pending/closed). In `rets_property` DaysOnMarket is the current listing's DOM; CumulativeDaysOnMarket sums across listing cycles. Lower DOM often signals stronger demand; higher DOM can mean a slower market or an overpriced listing.

Chunking exists because you can't hand a model 15,000 characters and expect a sharp answer — and you don't need to. Only the relevant paragraph matters. Slicing lets the system retrieve just the DOM entry rather than the entire glossary.

Why the pieces overlap. The slices step forward 780 characters at a time but are 900 long, so each one repeats the last 120 characters of the one before. Without that, a definition unlucky enough to straddle a boundary would be cut in half — the first piece trailing off mid-sentence, the second starting mid-thought, and neither making sense alone. The overlap guarantees anything reasonably short lands intact in at least one chunk.

What "a question" means here. Any message the router classified as knowledge — a definition or explanation request rather than a database lookup. "What does DOM mean?", "What is escrow?", "What's a cap rate?"

The whole thing, on one real question.

  1. Ahead of time, npm run rag:index turns each of the 21 chunks into 384 numbers — the same embedding process used for listings — and saves them to a file.
  2. You send "What does DOM mean?" The router sees it opens with "what does" and carries no measurement words, so it routes to RAG.
  3. The question itself is turned into 384 numbers the same way.
  4. Cosine similarity compares the question's vector against all 21 chunk vectors. The glossary's DOM chunk scores highest — it's about the same thing. The top 4 are kept.
  5. Those 4 chunks are pasted into a prompt that says, in effect: here is some reference text; answer the question using only this, and don't use outside knowledge.
  6. The model writes the answer, and the reply lists which files it came from — which is why you see a sources line.

One extra touch worth knowing: if the question names a city, the system also fetches a live market summary from the Week 5 agent and adds it alongside the document chunks. So a question can be answered from your written docs and current database numbers at the same time.

Why go to all this trouble? Ask a language model "what does DOM mean?" cold and it might say Document Object Model — correct in web development, useless here. Retrieval forces the answer to come from your glossary, in your domain. And if nothing relevant is found, it can say so rather than inventing something plausible.

If no API key is configured, it falls back to an extractive answer — lifting the most relevant sentences straight out of the chunks instead of writing prose. Less fluent, but it still cannot invent anything.

9. How the email's contents are decided

Nothing in the email is written by an AI. Every word is either fixed text in a template or a value pulled straight from the database. That's deliberate: it means a draft physically cannot invent a listing or a price that doesn't exist.

Three things have to be decided — who it goes to, what the subject line says, and what fills the body.

The recipient. If your message contains an email address, that's used. Otherwise it falls back to the configured EMAIL_USER, so a demo sends to yourself. If neither exists, it still shows you the draft but says plainly that it has nowhere to send it.

The subject. A small regex looks for a topic after "about", "for", "on" or "regarding", capitalises it, and uses that:

"Draft an email about Pasadena listings" → Subject: Pasadena listings "Email me a summary" (no topic found) → Subject: Property listings summary

The body — the WhatsApp path. This is what the demo uses, and it's the pragmatic one. The agent checks your message for two kinds of keyword and gathers accordingly:

market words (market, stats, trend, dom, price) → run the market stats agent listing words (home, listing, property, condo) → run the property search agent

Whichever fire, those agents run and their existing replies become the body — the same listing cards or market figures you'd have seen in the chat, collected into an email instead. If a message trips both, you get both sections. If it trips neither, it defaults to listings.

So "draft an email about Pasadena listings" hits the listing keywords, runs a property search, and the email body is that search's results. Plain text, not HTML.

The body — the CLI path. The email skill also has four purpose-built templates, chosen explicitly with --type, which produce proper styled HTML:

TypeGathersProduces
listing_alerta property search from your querya table of matching listings — address, price, beds/baths, sqft, photos, DOM
market_reportthe full Week 5 analysis for a citymedian and average close, $/sqft, DOM, list-to-close, inventory, plus six months of trend lines
property_summarythe single best-matching listingone detailed card with a comps note
recommendation_digestthe top 5 recommendationsa numbered list of homes you may like

These are ordinary string templates with the values substituted in. Three details worth noticing: every value is HTML-escaped before insertion (the same principle as the SQL placeholders — data never becomes markup), prices run through a currency formatter, and the row count is capped at 50 so a single email can't become a bulk export of the MLS.

Every generated email also carries a fixed footer: "IDX Exchange · Draft email · Requires human approval before send".

If you're asked which one the demo used: the WhatsApp path — it reuses the agents' own replies as the body. The four HTML templates are the richer version, reachable from the command line. That difference is honest to admit; it's the same split that produced the "two implementations drifted" point in your reflection.

9b. How the email queue works

Drafting writes a JSON record to a file on disk: a unique ID, recipient, subject, body, and status: "pending_approval". That's the entire drafting step — it has no ability to send.

Approving is a separate agent. It finds your most recent pending draft (or one you named by ID), flips the status to approved, and calls the send function. That function's first act is assertSendAllowed, which throws unless approval was passed in explicitly and the draft is in an approvable state. The status is written back as "sent" only after the mail server accepts it.

If sending fails — no credentials, for instance — the draft stays approved-but-unsent and can be retried. It fails closed, never open.

Following one message all the way through

Everything above, on one real message. You've already sent two: "Find me affordable homes in Pasadena" and "Under $1.2M". Now you send a third.

1 — The message arrives. WhatsApp hands over two things: the text, and who sent it.

text: "Only 3 bedrooms" sender: whatsapp:+1555… ← this is how it knows which conversation you're in

2 — Which specialist should answer? The routing patterns are checked in order. The word bedrooms is in the search vocabulary, nothing else matches, so it's a property search.

route: search → the property search agent handles this

3 — What did this message alone say? The message is read on its own, with no memory involved yet. Only one thing can be pulled out of it:

bedsMin: 3 bedsMax: 3 ← "only" means exactly 3, not 3-or-more city: — maxPrice: — ← this message says nothing about either

4 — Add it to what's already known. This is the step that makes conversation work. Your session already holds the results of the two earlier messages, and the new value is layered on top. Nothing this message didn't mention gets touched:

before this message after merging ───────────────────── ───────────────────── city: Pasadena city: Pasadena ← kept maxPrice: 1,200,000 maxPrice: 1,200,000 ← kept bedsMin: — bedsMin: 3 ← added bedsMax: — bedsMax: 3 ← added

Those are real values — that sequence is pinned by a test. Without this merge, "Only 3 bedrooms" would search every 3-bedroom home in California.

5 — Turn that into a database question. Each filter that has a value adds one condition and one value, kept in matching order:

question: SELECT … FROM rets_property WHERE L_Status = 'Active' AND L_City = ? AND L_SystemPrice <= ? AND L_Keyword2 = ? values: ["Pasadena", 1200000, 3]

The values travel separately from the question, so nothing you typed can change what the question asks.

6 — Ask the database. It runs against the active-listings table and comes back with matching rows — five of them for the reply, and never more than fifty in any case.

7 — Make it readable. Raw database rows are turned into something you'd want to read on a phone:

1) 1247 N Los Robles Ave, Pasadena, 91104 $1,150,000 · 3 bd / 2 ba · 1,640 sqft · 24 photos 2) 862 E Mountain St, Pasadena, 91104 $1,095,000 · 3 bd / 2 ba · 1,510 sqft · 31 photos

Illustrative addresses — the real ones come from your database.

8 — Remember what was shown. The results are saved back to your session. That's what makes the next message work: when you say "I like the first one", it knows which listing you mean.

9 — Reply. The text goes back out through the same handler it came in on, and your phone buzzes.

The one step to remember: step 4. Everything else is plumbing — reading a message, building a query, formatting a result. Step 4 is what turns eight separate questions into one conversation.

During the live demo

What to say, word for word

Read the quoted lines out loud. The grey note under each is for your own understanding — and for follow-up questions — not to be recited.

The opening — about 60 seconds

Dense and factual: what the system is, what it queries, how it routes, and what technique sits behind each agent. No warm-up story — the specifics do the work.

This is the IDX Multi-Agent Real Estate Assistant. It runs over WhatsApp and queries two MySQL tables from the California MLS — rets_property, which holds active listings, and california_sold, which holds closed sales.

Every message enters at a single point. A classifier reads it and routes it to one of seven agents: property search, market statistics, semantic search, recommendations, a knowledge agent, and two for email — one that drafts, one that sends. Eight routes in total, because a message asking two things at once runs two agents in parallel and merges the answers.

The method differs by agent. Structured search turns English into parameterized SQL. Semantic search embeds each listing as a 384-dimension vector and ranks by cosine similarity. Recommendations blend both — roughly sixty points of structured similarity, forty of embedding similarity — then price-check the result against sold comparables. The knowledge agent retrieves from indexed documents rather than generating from memory.

I'll send it eight messages. The last one is the one it won't send by itself.

Be ready for these

Questions you'll get

Click any question to see an answer you can say in your own words. If you're asked something you genuinely don't know, say so and say what you'd check — that reads far better than guessing.

How does it know which agent to use?

A function called classifyIntent reads the message and matches it against patterns. Words like "find", "bedroom" or "under $" signal a search; "market", "trend" or "days on market" signal statistics; "what does X mean" signals a definition question; "approve" signals an email approval.

If pushed on why not use an LLM to route: pattern matching is instant, free, and testable — every route is pinned by a unit test. An LLM router would be more flexible but slower, less predictable, and harder to prove correct.

What's the difference between the two kinds of search?

Structured search turns your words into database filters — city, price, bedrooms — and does an exact lookup. Semantic search is for descriptions that can't become filters, like "charming with lots of light". It compares meaning instead of matching fields.

The router prefers structured search whenever it finds real filters, and falls back to semantic search for pure description.

Why embeddings instead of a keyword search?

Keyword search fails on synonyms. "Cozy cottage" and "charming bungalow" share no words but mean nearly the same thing. Embeddings place text in a mathematical space where similar meanings sit close together, so the match works regardless of the exact words used.

How does it remember the conversation?

Each user has a session, keyed to their WhatsApp ID, holding the filters from previous turns. A new message is parsed and merged into what's already there rather than replacing it — which is why "under $1.2M" keeps the city from two messages ago.

The filters are stored as ranges (a minimum and a maximum for bedrooms and price) specifically so they can be narrowed one message at a time.

Could it send an email by accident?

No. Drafting and sending are separate code paths. Drafting saves to a queue and returns a preview — it has no ability to send. The send function begins by calling assertSendAllowed, which throws an error unless approval was explicitly passed in. Nothing automated — no scheduled task, no background job — has a route to it.

There are two more limits alongside it: results are capped at 50 rows so it can't bulk-export listing data, and credentials are stripped from any log or preview.

How do you know it works?

105 automated tests, all passing, plus a clean typecheck. They're written to run anywhere — no database, no network, no API keys — by testing the pure logic: the query builders return the SQL and parameters they'd send, and the tests check those rather than hitting a real database.

What was the hardest part?

An honest, specific answer: the two databases don't share a naming convention. City is L_City in one table and City in the other; bedrooms are L_Keyword2, bathrooms are LM_Dec_3. And the amenity flags aren't true/false — they're text, and the same column might say 'True', '1', or 'Yes'. Checking for = true silently returns almost nothing, which looks like an empty result rather than a bug.

What would you do differently?

Build the routing alongside each feature instead of at the end. The orchestrator was added in Week 9, after six skills already existed — and it turned out several working features had no route to them. Semantic search was fully built and tested, but no user could reach it, because it was never registered with the router.

The lesson: a feature isn't done when the code works. It's done when a user can reach it. Integration is a feature, not glue.

How do you prevent SQL injection?

Every query is parameterized. The SQL contains ? placeholders and the values are passed separately to the driver, so user input is never assembled into the query text. There's no string interpolation of user input anywhere in the project.

Why run the AI model locally instead of calling an API?

The embedding model runs on the machine by default, so there's no API quota, no key needed to demo it, and results are reproducible. A cloud model is still available behind one environment variable if you want higher quality.

One catch worth knowing: the two models produce different-sized vectors (384 vs 768), so the cache records which model built it and refuses to mix them.

What happens if it doesn't understand a message?

It falls back to a message asking you to rephrase. It doesn't guess an agent, and it doesn't invent an answer.

Which embedding model, and why that one?

all-MiniLM-L6-v2 — a small, well-established sentence-embedding model that runs locally in about a fifth of a second per query once loaded. It produces 384-number vectors, which is small enough to keep thousands of listings in memory and compare them instantly.

It was chosen over a cloud model because it needs no API key, has no quota, and gives identical results every run — all of which matter for a demo. The cloud option (Gemini, 768 numbers) is still available behind one environment variable if higher quality is wanted.

Why 900-character chunks with a 120-character overlap?

Chunks have to be small enough that a retrieved passage is actually about one thing, but large enough to keep a full definition or a column list intact. 900 was tuned upward from a 600 starting point because the MLS field definitions were being split mid-list.

The overlap is the important part: if a definition happens to fall exactly on a boundary, without overlap it gets cut in half and neither piece makes sense alone. Repeating 120 characters into the next chunk means anything short enough always appears whole somewhere.

How would this scale to millions of listings?

Honestly — the similarity search wouldn't, as written. It compares the query against every cached listing one at a time, which is fine for thousands but linear in the number of listings.

At serious scale you'd swap that brute-force scan for a vector database with an approximate nearest-neighbour index, which finds the closest matches without checking every one. The rest of the design — the routing, the SQL, the approval gate — wouldn't need to change.

This is a good answer to give: it shows you know the limitation rather than not having noticed it.

One honest note. If you're asked something you don't know, the strongest answer is "I'm not certain — I'd check [the file, the test, the schema]." Nobody expects total recall of a twelve-week project, and a confident wrong answer is much worse than an honest gap.
